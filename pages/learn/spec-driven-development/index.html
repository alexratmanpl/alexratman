A 10-minute scroll about spec-driven development

Write it down
before you build it

"Spec-driven development" is a long name for a simple habit. Before an AI builds anything, you write down what you want, in plain sentences. This page follows one small example: an app that splits a restaurant bill. Short questions along the way let you try each idea. Want to try it right away? Go to step 7. Step 1 · What it is

First, write down what the app should do

Many people start by chatting with an AI: "Build me an app that splits a restaurant bill." The AI then makes lots of small decisions on its own: how much tip to add, how to round the amounts and what to save. In this guide, an "app" means anything you build this way, such as a calculator, a form or a small website.

I learned how much that matters on my own "about me" page. I gave an AI model, Claude, my CV and asked it to build the page. But a CV is only a summary, so the AI filled the gaps by guessing. A word like "audit" made it think I did deep analysis. My real work was more routine: "controlling", which means regular checks that things were done as they should be. It also made up details about my programming skills and my work for earlier employers. People call this "hallucinating".

By my own estimate, the picture of me was 60 to 70% true. That is not enough for a page about myself. The AI needed room to ask me questions first.

Spec-driven development changes the order. First you write down what the app must do, even roughly. The AI asks you about everything that is unclear, and together you finish the description. Then the AI builds from it, and you check the result against it. That leaves fewer gaps for the AI to fill with guesses.

This written description is called a spec, short for "specification". For the bill splitter, it looks like this.

Bill splitter · what it must do
  1. I type the total bill and the number of people.
  2. The app shows what each person pays, with cents, like 12.50.
  3. I can add a tip as a percentage. The app then shows the new total and each person's share.
  4. If a box is empty, or the number of people is zero, the app shows a short message instead of a result.

A real spec would be longer. What matters is the style: plain words, one rule per line. You can check it without reading code, the instructions a computer follows.

Not every line is as good as these. Below are five lines that someone might write for the same app.

Your turn

The AI builds from the words in your spec. If a line is vague, it has to guess, and its guess may not be what you meant. Keep a line if you could check it by trying the finished app. Rewrite it if two people could read it in different ways. Read each line that someone wrote for the bill splitter. Keep it, or rewrite it?

  1. I type the total bill and the number of people. Keep. It says who does what, and you can try it in seconds.
  2. The app should feel friendly and modern. Rewrite. Nobody can check "friendly" or "modern". Ten people would build ten different apps. Try this Say what you would see or do: "I see each share as soon as I have typed both numbers."
  3. If a box is empty, or the number of people is zero, the app shows a short message instead of a result. Keep. It names the cases and says what happens. You can try both in a minute.
  4. The app handles tips properly. Rewrite. "Properly" hides the choices: a percentage or a fixed sum, before or after tax. The AI would pick for you. Try this I can add a tip as a percentage. The app then shows the new total and each person's share.
  5. When I close the page and open it again, both boxes are empty. Keep. It says what you will see, so it is easy to check. Close the page, open it again, and look at both boxes.

For your own spec, ask yourself about every line: how would I check this? A word such as "friendly" or "properly" usually means the line needs a rewrite.

To start, tell an AI chat your idea and ask it to interview you, then write the spec as short numbered sentences. Step 7 shows this in a made-up chat. You need no special software: a normal AI chat and a file of your own (Word, Google Docs or Notepad) are enough. Programmers have tools built around the idea, such as Spec Kit and Kiro, but you can ignore them for now. If an AI ever asks you to install software or type commands (typed lines in a special window), ask it for an easier way.

Step 2 · Building in stages

Then build it in small stages, and check each one

Don't ask the AI for the whole app at once. Ask for one stage at a time, and read what you get before you say "next". The tools from step 1, Spec Kit and Kiro, are both built around stages like these.

The bill splitter, stage by stage

Click a stage to see what happens in it.

Who does it You tell the AI the idea. It writes the spec and asks what's unclear.

What you get

A spec: a page of plain sentences.

For example "The app shows what each person pays, with cents, like 12.50."

What you check

Is this what I meant? Is anything missing?

Changing a sentence is quick. Finding out later that the whole app is built on a wrong guess is slow. So when something is wrong, go back to the stage where it started, not the stage where you noticed it. The same goes when you change your mind: change the spec first, then ask the AI to update the app. The pauses do add reading, though, and I come back to that in step 6.

Your turn

Read each problem. Pick the stage where it started, then pick what you do.

  1. The leftover cent

    The AI shows its plan for the bill splitter. You notice that 100.00 shared by 3 people is 33.33 each, which leaves 1 cent. Nobody has said what the app should do with it.

    • The spec has no line about rounding.
    • The plan follows the spec, so it says nothing about it either.
    • Nothing is built yet.

    Where did it start? Best answer: Describe. The gap is in the spec, so that is where it started. One new line fixes it before anything depends on the answer.

    • Plan. The plan only follows the spec. Patch the plan and the spec still has the gap, so the next plan can lose the fix.
    • Split into tasks. The tasks come from the plan. You cannot fix a missing rule by adding a task.
    • Build. Nothing is built yet. If you wait, the AI picks a rule itself, and you meet its choice only when a check fails.

    What do you do? Best answer: Add a line to the spec, then ask for a new plan. The new line then flows through the plan, the tasks and the checks, so every stage learns the rule.

    • Tell the AI to round up when it builds. It works once. The rule lives only in this chat, and a new chat or a later change can lose it.
    • Wait and see what the app does. You get an answer, but the AI chose it, and you will not know why.

    What you could send Add this line to the spec: "If the bill doesn't divide evenly, the app rounds each share up to the next cent." Then update the plan.

  2. A check that fails

    Task 2 is done. You run its check: add 10% to a bill of 100. The app shows 110.00 in total but 27.5 each, not 27.50. The spec line says "with cents".

    • The spec line is clear.
    • The task is the right size, and it has a check.
    • Only the app is wrong.

    Where did it start? Best answer: Build. The code for this task is wrong, and the check shows exactly where.

    • Describe. The spec already says "with cents". Nothing is missing there.
    • Plan. The plan covers the tip, and its pieces are right. The fault is in how this piece was built.
    • Split into tasks. The task is the right size, and its check did its job: it caught the fault.

    What do you do? Best answer: Tell the AI the check failed, say what you saw, and ask it to fix this task. The AI sees the failed check and the spec line, fixes the task, and you run the check again.

    • Rewrite the spec line about cents. The line is already clear. Loosening it to fit the app would hide the fault, not fix it.
    • Start the whole plan again. Task 1 passed, and task 2 is nearly right. Starting over throws away work that is fine.

    What you could send Task 2 failed its check. I see 27.5 each, but line 2 says "with cents". Please fix task 2 only.

The rule of thumb Go back to the stage where a problem started. A gap in the spec goes back to the spec. A fault in the app is fixed in the build.

Step 3 · Checking the work

Turn each line of the spec into a check

A check (engineers say "test") looks at one line of the spec and ends in pass or fail. When you are happy with the spec, ask for the checks in the same chat, before anything is built. For example: "For each line of the spec, add one check I can do myself, written as a plain sentence." Then save the checks in the same file as your spec.

Your job is to read each check and ask: does this say what I meant? Then try it yourself on the finished app. A normal AI chat usually can't do that for you, because it can't open your app.

The first four lines of the bill splitter are shown below, each with its check. Press the button to run them. It's a made-up run.

Four spec lines, four checks
  • Line 1 Spec I type the total bill and the number of people. Check Open the app. You see one box for the total and one for the number of people. Not run
  • Line 2 Spec The app shows what each person pays, with cents, like 12.50. Check Type 100 and 4 people. You see 25.00 each. The app showed 25 each. Not run
  • Line 3 Spec I can add a tip as a percentage. The app then shows the new total and each person's share. Check Add 10%. You see 110.00 in total and 27.50 each. Not run
  • Line 4 Spec If a box is empty, or the number of people is zero, the app shows a short message instead of a result. Check Clear the total box. A short message appears, not a number. Not run
Not run yet.

Passing every check is a good sign, but only for the lines that were written down. Show the app to other people only after it passes your checks.

Checks look at one line each. A review is different: you, or a new AI chat, reads all the work and compares it with the spec. For a review, open a new chat and paste in your spec and the finished app. Ask it to compare them line by line. If you are not sure what to paste, ask the chat that built the app to show its latest full version in one message.

A new chat is better, because it didn't write the work. The docs for Claude Code, Anthropic's coding tool, say the same. Ask more than once, too. In Cloudflare's tests of a security checker for code, one run found only about half of the problems that repeated runs found. Those tests were about a code checker, not a chat, so asking again is my own advice.

A check is worth less if the AI can change it. When Anthropic launched its AI model Claude 3.7 Sonnet in February 2025, it published a report on it. The report says that in coding tools like Claude Code, the model occasionally took shortcuts to pass tests (the same thing as checks). Most often it gave back the exact answers the tests expected. That is like a student copying the answers instead of working them out. The model also changed tests to match its code. Anthropic says it added partial fixes before launch, and that they significantly reduced how often this happened in typical use. So if an AI changes a check, compare it with your saved copy and ask why.

Your turn

Read each job. Pick what you do, then pick the reason.

  1. A check for the tip line

    Spec line 3 says: "I can add a tip as a percentage. The app then shows the new total and each person's share." You ask the AI for one check you can do yourself.

    • 100 shared by 4 people is 25.00 each.
    • 10% of 100 is 10.

    What do you do? Best answer: Add 10% to a bill of 100 shared by 4. You see 110.00 in total and 27.50 each. You can work out 110.00 and 27.50 yourself. The check ends in pass or fail.

    • Try some tips and see whether the app looks right. "Looks right" has no answer that can fail. Two people would judge it differently.
    • Ask the AI whether the tip works. The AI that built the app would mark its own work. A check you can do yourself does not depend on its answer.

    Why? Best answer: It uses numbers I can work out myself, so the result is pass or fail. That is the point of a check. You do not need to trust anyone to know whether it passed.

    • It covers every tip someone could type. No single check can do that. A good check uses numbers you can work out yourself, so the answer is clearly pass or fail.
    • The AI knows the app best, so it can judge. The AI that wrote the work is the least likely to see its flaws. A new chat reviews better, and your own numbers check better.

    How to ask for checks For each line of the spec, add one check I can do myself, written as a plain sentence.

  2. The AI changed a check

    Task 2 fails its check. You expect 110.00 in total, but the app shows 100.00. You tell the AI. It replies: "I have updated the check, so it now passes."

    • The spec line has not changed.
    • Your saved copy of the checks is in a file.

    What do you do? Best answer: Compare the check with your saved copy, and ask why it changed. The spec did not change, so the check should not change either. Your saved copy shows what it said before, and the AI must explain.

    • Accept it. The check passes now. It passes only because it was changed to match the app. The app is still wrong, and now nothing says so.
    • Ask the AI to drop all the checks, since they cause trouble. Without checks, nothing tells you whether the app does what the spec says.

    Why? Best answer: A check the AI can change is worth less. Anthropic's report on one of its models says it sometimes changed tests to make them pass. A saved copy lets you notice.

    • Checks are only for programmers. A check written as a plain sentence is meant for you to do yourself.
    • The AI knows the app best, so its new check is probably right. The spec line has not changed, so the check should not have changed. An AI can change a check so that it passes, without fixing the app.

The rule of thumb A good check has an answer you can work out yourself. Keep your own saved copy, and ask why whenever a check changes.

Step 4 · Safety and watching

Write down the safety rules, and who is told when something breaks

If a spec says nothing about what the app saves, or who is allowed to see it, the AI picks something. Sometimes that's wrong, and nobody notices until it matters.

A real case shows the risk. Moltbook is a social website. Its founder said he built it with AI and "didn't write a single line of code". In February 2026 the security company Wiz reported that anyone could read and change the information the site stored. Its article gives several counts of what was exposed. The headline figure is about 35,000 email addresses. The site's access rules, which say who is allowed to see or change what, hadn't been set up properly. Wiz says the Moltbook team secured it within hours, with its help.

I'm not saying a spec would have prevented that. Wiz adds that today's AI tools don't yet think about security or about who gets access. A careful human check of the settings still helps. You can do that check yourself. A spec gives you somewhere to write the rules down, so there's something to check.

You don't have to invent the safety questions. In June 2026 Cloudflare, a company that protects websites from attacks, released a free security-audit skill. A skill is a ready-made set of instructions for an AI tool, and this one makes an AI act as a security auditor. I took four questions from its checklist and put them in my own words. I think they suit any spec:

Four safety questions to ask your AI about any spec
  1. Who is allowed to see or change what? Being signed in doesn't mean being allowed to see everything.
  2. Where are passwords and other secret codes kept? Not written into the app itself.
  3. Is any shortcut you used while building, such as a login that lets anyone in, still open once people use the app?
  4. When something goes wrong, does the app show technical details that could help someone break in?

Paste these four questions into your AI chat with your spec, and ask it to answer each one. Read the answers yourself, and ask the AI to explain anything you don't follow. The skill itself needs programmer tools, so the last section of this page only points to it.

One more line belongs in a spec: who is told when the app stops working. Engineers call this monitoring: you hear about trouble early, and can see enough to find the cause. Here, people care that the app works when they open it, so the line says who is told when it stops. That can be you. Google's engineers give the same advice: start from what users care about, not from what you can measure.

Your turn

Read each problem. Pick the question that would have caught it.

  1. Customers can read each other's records

    A small booking app keeps its customers' names and phone numbers. A customer signs in with a normal account and finds that they can read every other customer's record too.

    • The customer signed in with a normal account.
    • Every record was readable.
    • Nobody wrote down who may read what.

    Which question would have caught it? Best answer: Who is allowed to see or change what? Nobody wrote down who may see what, so the AI set no rules. This question makes it list them, and the gap shows. The Moltbook story had the same kind of gap.

    • Where are passwords and other secret codes kept? Secret codes are the keys to something that is locked. Here the customer had a normal key, and nothing limited what it opened.
    • Is any shortcut from building still open? A shortcut means something was switched off for testing. Nothing here says so. The customer signed in the normal way.
    • Does the app show technical details when something goes wrong? No error message is involved. The records simply opened.
    • Who is told when the app stops working? That is about noticing trouble. Nobody was told, but the first problem is that any customer can read everyone's records.

    What you could send Who is allowed to see or change what in this app? List every kind of person, and say what each one can do.

  2. A password in the page

    A small web tool lets staff look up orders. The AI typed the password for the order list straight into the page's code. The tool is online, and anyone who opens the page can read that code.

    • The password is written inside the code of the page.
    • Anyone who opens the page can read its code.
    • Staff sign in correctly, and each person sees only their own orders.

    Which question would have caught it? Best answer: Where are passwords and other secret codes kept? A password written into the code can be read by anyone who opens the code. This question makes the AI say where each secret code is kept, so you can have it moved out of the app itself.

    • Who is allowed to see or change what? The rules about who sees which orders are fine. The trouble is that a password is out in the open, so someone could skip the rules altogether.
    • Is any shortcut from building still open? Typing the password in was quick, but a shortcut question looks for protection that was switched off, such as a login that lets anyone in. Here the problem is where the password sits.
    • Does the app show technical details when something goes wrong? No error message is involved. The password sits in the code all the time.
    • Who is told when the app stops working? Hearing about trouble matters, but nothing has stopped working. The password is exposed now.

    What you could send Where are passwords and other secret codes kept in this app? List every place one is written in the code, and tell me how to keep them out of the app itself.

  3. The test login

    While building, the AI added a "skip login" button so you could test faster. The app is online now, and the button still works.

    • It was added only for testing.
    • Nobody removed it before launch.
    • Anyone who finds it gets in.

    Which question would have caught it? Best answer: Is any shortcut from building still open? A shortcut for testing is still open. This question makes the AI list what was switched off or skipped while building.

    • Who is allowed to see or change what? This is about the rules once a person is in. It would not look for a button that skips the login altogether.
    • Where are passwords and other secret codes kept? Secret codes are a separate risk. Nothing here says one is exposed.
    • Does the app show technical details when something goes wrong? No error message is involved.
    • Who is told when the app stops working? Noticing trouble matters, but the first fix is to close the way in.

    What you could send List everything that was switched off, skipped or made easier while you built this app, and tell me which parts are still open.

  4. A long error message

    A customer types a wrong date into the booking tool. The tool shows a long screen of technical text, with file names and the name of the database it uses.

    • The customer made a small mistake.
    • The screen showed file names and the database name.
    • Everyone may use the tool, and no password is shown.

    Which question would have caught it? Best answer: Does the app show technical details when something goes wrong? File names and the database name help someone plan an attack. This question makes the AI check what the app shows when something goes wrong, so a customer sees a short, plain message instead.

    • Who is allowed to see or change what? Everyone may use the tool, so that is not the gap. The trouble is what the error screen gives away.
    • Where are passwords and other secret codes kept? No password or secret code appears on the screen.
    • Is any shortcut from building still open? A shortcut question looks for protection that was switched off for testing, such as a login that skips. This one is about what the error screen shows.
    • Who is told when the app stops working? Telling someone matters, but the problem here is what the customer can see.

    What you could send When something goes wrong in this app, what does the screen show? Make it show a short, plain message to the customer, and keep the technical details out of sight.

  5. A failure nobody saw

    The bill splitter runs on a small website. It stopped working at midnight. Nobody knew until a friend sent a message the next afternoon.

    • The AI built the app, and it passed all its checks.
    • No line in the spec says who is told.

    Which question would have caught it? Best answer: Who is told when the app stops working? The spec needs a line that says who is told when the app stops, and how. That can be you. Without it, the app fails quietly.

    • Who is allowed to see or change what? Nothing here is about who sees what.
    • Where are passwords and other secret codes kept? Nothing here suggests a secret code was exposed.
    • Is any shortcut from building still open? The app stopped. Nothing was left open.
    • Does the app show technical details when something goes wrong? Nobody saw an error screen, so no details leaked.

The rule of thumb Match the question to the gap: who may see what, where secrets live, what testing left open, what an error shows, and who is told.

Step 5 · When something breaks

When something breaks, a spec helps you start again, but it can't bring back your data

Apps do break: a change goes wrong, or someone deletes the wrong file. So save your spec, your plan and your checks as files you can find again. A new AI chat can then read them and try to build the app again. What you get back depends on what you lose.

What you could lose, what helps, and whether you can get it back
What you loseWhat helpsCan you get it back?
The chat you built it in your conversation with the AIThe spec, saved as a fileNo, but you can carry on
The app itself the program that does the workThe spec, plan and checksMaybe, by rebuilding
The data it keeps such as a list of past billsNot the specOnly from a saved copy

A new chat usually starts from nothing, so everything you explained in the old one is gone. Give it the saved spec, and it continues from there. Anthropic, the company behind Claude, gives similar advice: once the spec is complete, start a new chat to build from it. If the app itself is gone, a new chat can read your spec, plan and checks and build a new copy. The data is different, because the spec describes the app and doesn't contain the data.

Don't expect a perfect copy. An AI can answer the same question differently each time. Birgitta Böckeler, an engineer at the technology company Thoughtworks, looked at three spec tools. With one of them she had the AI write the code several times from the same spec, and the results varied. So run the same checks on the rebuilt app as on the first.

If your app keeps data, such as past bills, that data needs its own backup, because the spec holds none of it. The bill splitter in this guide saves nothing, so it needs none. For a small tool that does keep data, ask the AI for a button that saves everything, for example as a spreadsheet file.

Your turn

Read each case. Pick what you reach for, then pick what comes back.

  1. The chat is gone

    You planned the bill splitter in one long chat. You close the tab by mistake, and the chat is gone. The app on your computer is fine, and your spec is saved in a file.

    • The app still works.
    • The spec is a file on your computer.

    What do you reach for? Best answer: The saved spec. A new chat starts from nothing. Give it the spec, and it carries on from there.

    • A rebuild from the saved spec, plan and checks. The app is fine, so there is nothing to rebuild. A new chat only needs to know what the app must do.
    • A backup copy of the data. The app keeps no data, and a backup would not tell a new chat what to do.

    What comes back? Best answer: You carry on where you were. The spec holds what the app must do, so the new chat can start from it. You lose the old chat, not the work.

    • A new copy of the app that you must check. The app is not lost, so there is no new copy to check.
    • Only what the backup holds. There is no backup here, and none is needed. The app keeps nothing.

  2. The app file is gone

    Your laptop is stolen. The only copy of the app was on it. Your spec, plan and checks are in an online folder.

    • The spec, plan and checks are saved online.
    • The app itself is gone.
    • The app keeps no data.

    What do you reach for? Best answer: A rebuild from the saved spec, plan and checks. A new chat reads them and builds a new copy. The plan shows what to build, and the checks show whether it works.

    • The saved spec. It is a start. Without the plan and the checks, you cannot tell whether the new copy is right.
    • A backup copy of the data. The app keeps no data, so there is nothing to back up. What you need is the means to build it again.

    What comes back? Best answer: A new copy of the app that you must check. A new chat can write the app again, but it may differ from the old one. Run the same checks on it.

    • You carry on where you were. The old app is gone. A new one has to be written first.
    • Only what the backup holds. Nothing was backed up, because the app keeps nothing.

  3. The past bills are gone

    The app keeps a list of past bills. Someone deletes the file that holds them. The app still works, and you saved a backup file last week.

    • The app itself still works.
    • The list of past bills is gone.
    • Your backup file is a week old.

    What do you reach for? Best answer: A backup copy of the data. The spec describes the app, not what people typed into it. Only a saved copy of the data holds the bills.

    • The saved spec. The spec has no bills in it. It describes the app, and you still have the app.
    • A rebuild from the saved spec, plan and checks. Rebuilding gives you a fresh app with an empty list.

    What comes back? Best answer: Only what the backup holds. Everything up to the day you saved the file comes back. Bills added since then are gone.

    • You carry on where you were. Only if the bills were in the spec, and they are not.
    • A new copy of the app that you must check. The app is not the problem. The data is.

The rule of thumb The spec brings back the app, not what people typed into it. Keep a copy of the data somewhere else, and open it once to check.

Step 6 · The good and the bad

What's good about it, and what isn't

Here is what people have reported, for and against. Use it to decide how much spec your own project needs. Step 7 helps you choose.

Good points
  • +

    It aims at a common problem: things nobody wrote down

    In a 2014–15 survey of 228 companies, 48% ranked incomplete or hidden requirements among their five most critical problems. The survey was about software projects in general, not about specs. Hidden requirements are things the software must do that nobody wrote down. A spec is one way to put them in writing, in plain words that you and the AI can both read.

  • +

    Written notes help an AI pick up where it left off

    Anthropic's engineering blog describes AI programs that work on one project over many sessions (separate runs). It says "each new session begins with no memory of what came before". Part of its fix is written notes: a progress file and a feature list that the next session reads at the start. In my view, a saved spec does the same job.

  • +

    A review can name the requirement behind a problem

    InfoQ, a news site for software engineers, published a small trial in 2026. Five reviewers each reviewed AI-generated banking software twice: once with the approved spec and design documents, and once without them. With the spec, 81% of what they found could be tied to a named requirement. Without it, none could. They found about the same share of the known problems either way. So the spec gave them something to point to, not better reviews. The author calls the result a "strong pilot signal", not "confirmatory proof". With only five reviewers, treat it as a hint.

Problems
  • −

    More to read, and too much for small fixes

    Böckeler asked Kiro to fix a small bug (a mistake in a program). It turned that one bug into a long list of requirements. There were four "user stories" (short notes on what a user wants) and sixteen "acceptance criteria" (conditions the fix had to meet). She said the workflow was like "a sledgehammer to crack a nut": far too heavy for a small job. Kiro has since added a spec type for bug fixes. In the trial above, reviews took about 22 minutes longer with the spec and design documents.

  • −

    Plans change, and the spec goes out of date

    Programmer Kent Beck, quoted on Martin Fowler's site, says the descriptions of spec-driven development he has seen stress writing the whole spec first. He finds it strange to assume that you will learn nothing while building that could change the spec. A Thoughtworks writer who supports the approach says "spec drift" and hallucination are "inherently difficult to avoid". By spec drift I mean the spec and the app slowly no longer matching.

  • −

    The AI may not follow it

    In one example from September 2025, Böckeler asked Spec Kit to build on existing code. The AI ignored the notes saying parts of it already existed and wrote them all again. She notes that the tools may have changed since.

    Saved instructions can help the AI follow your rules. In Claude, you can keep them in a skill, or in a project (a separate workspace with its own chats and files). Anthropic says a skill teaches Claude a task "in a repeatable way". Even so, its guidance for Claude Code says "there's no guarantee that it'll follow your instructions", and that includes a skill.

Step 7 · Try it yourself

See it two ways, then try it on something real

A made-up example

The same idea, asked two ways
Just ask

You: Build me an app that splits a restaurant bill.

AI: Done! I built a clean, modern bill splitter with tip options. It works on any device.

You: Did you decide anything I didn't ask for?

AI: Yes, three things. I set the tip to 10% unless you change it. I round each share up to the next whole number. I also made the app save your last 10 bills in your browser.

Spec first

You: Here is my spec for an app that splits a restaurant bill.

  1. I type the total bill and the number of people.
  2. The app shows what each person pays, with cents, like 12.50.
  3. I can add a tip as a percentage. The app then shows the new total and each person's share.
  4. If a box is empty, or the number of people is zero, the app shows a short message instead of a result.
  5. When I close the page and open it again, both boxes are empty.
  6. When I make the window narrow, like a phone screen, nothing is cut off.

Ask me about anything unclear before you build.

AI: Thanks. Before I build anything, one thing is unclear. 100.00 shared by 3 people is 33.33 each, and that leaves 1 cent. What should the app do?

You: Round each share up, so everyone pays 33.34.

AI: Good. I added line 7: "If the bill doesn't divide evenly, the app rounds each share up to the next cent." Here is my plan. I grouped related lines into five tasks, and each task has a check you can run yourself.

  1. Two boxes and the result. Check: Type 100 and 4 people. You see 25.00 each.
  2. The tip. Check: Add 10%. You see 110.00 in total and 27.50 each.
  3. Empty boxes and zero people. Check: Clear the total box. A short message appears, not a number.
  4. The leftover cent. Check: Type 100 and 3 people. You see 33.34 each.
  5. Nothing saved, and a narrow window. Check: Close the page and open it again: both boxes are empty. Make the window narrow: nothing is cut off.

You: Start with task 1.

AI: Task 1 is done. Save the app as splitter.html and open that file in your browser. Run its check: type 100 and 4 people. What do you see?

You: I see 25.00 each.

AI: Task 1 passes. Say "next" when you want task 2.

Try it on something real

My own try

I took the spec-first way for my own "about me" page. I started from a written spec. Then the AI asked me about my background, what I needed and the shape the page should take. In one conversation with Claude, we reached my page as it is today. For me, it was the fastest page I have built in my career, and the one that fitted my needs best.

If people will judge your idea by how it looks, such as a home page, draw it first. Draw It Before You Build It shows how.

How much spec does a job need? The dial below has four settings, my own suggestion. Try three jobs, then use the setting that fits your idea. The last two are for bigger jobs.

Your turn

Read each job. Turn the dial to the setting you would choose.

The settings, from least to most:

  • One sentence. Tell the AI what you want in one sentence, such as "Make the title blue", and check the result. Skip the spec.
  • A short spec and a few checks. Plain sentences for the main rules, and a check for each. An app that saves nothing has nothing to back up. A bill splitter or a packing checklist is about this size.
  • The full spec, with safety rules. Add rules for who may see what, where passwords and other secret codes are kept, and what happens when saving fails. Give each rule a check. The four safety questions in step 4 ask about these. Ask them again in a new chat, because one chat can miss things. Back up what the app saves, as step 5 explains.
  • The full set, and keep watching. Do everything in the full spec, then keep checking now and then that it still works once people use it. If many people will rely on it, a ready-made service, such as an online form or booking tool, may be the safer choice.

  1. Make a title blue

    The title on your own web page is black. You want it blue.

    • One sentence says it all.
    • You will see the result at once.
    • Nothing is saved, and nobody else uses it.

    Best setting: One sentence. One sentence is enough. You see the result at once, and a wrong guess costs a few seconds.

    • A short spec and a few checks. A spec and checks for a colour change take longer than the change. The screen already shows you whether it worked.
    • The full spec, with safety rules. Safety rules for a colour? There is nothing to protect. You would spend an hour on a job that takes a minute.
    • The full set, and keep watching. Far too much for a title colour. Nobody relies on it, so there is nothing to keep watching.

    When the job fits in one sentence and you can see the result, skip the spec.

  2. A sign-up sheet for a school club

    A school club wants a sign-up form. Parents type a child's name and a phone number. The club leader reads the list.

    • The form keeps other people's details.
    • More than one person will use it.
    • A mistake could expose phone numbers.

    Best setting: The full spec, with safety rules. Rules, checks and the safety questions, done again in a new chat. The form keeps other people's details, so the safety rules are part of the job.

    • One sentence. "Make a sign-up form" leaves everything to the AI: where the names are saved, and who can read them. Nobody has decided.
    • A short spec and a few checks. Rules and checks help, but phone numbers need safety rules too: who may see them, and where secret codes are kept.
    • The full set, and keep watching. More than a club list needs. Watching it all the time matters when many people rely on it.

    Other people's details raise the setting, even for a small tool.

  3. A booking tool for a clinic

    A clinic wants patients to book online. Reception staff use the list all day. If it stops, patients miss appointments.

    • Many people rely on it every day.
    • It keeps personal details.
    • A failure costs real appointments.

    Best setting: The full set, and keep watching. The full spec, and someone who keeps checking it works once people use it. For a job this big, a ready-made booking service may be safer than building your own.

    • One sentence. A one-sentence request for a tool people depend on leaves every rule to the AI.
    • A short spec and a few checks. No safety rules for patients' details, and nobody is told when it stops. That is too little.
    • The full spec, with safety rules. Close, but it stops at launch. When many people rely on a tool, someone must keep checking that it still works.

    The more people rely on it, the more you keep checking after launch.

The rule of thumb Match the spec to the risk. A small change needs one sentence. Other people's details need safety rules. A tool many people rely on needs all of it, and someone watching.

Or sketch it as a diagram

A spec can also be drawn as a diagram of what depends on what. Each box is one line of the spec, and an arrow points to a line that needs it. Kiro tracks the same thing for tasks: it builds a dependency graph from its task list.

Bill splitter · which line needs which
  • Line 1 Type the total and the number of people
    • Line 2 Show what each person pays
      • Line 3 Add a tip
    • Line 4 Show a message if a box is empty

The first four lines of the spec in step 1. An arrow points to a line that needs the one it comes from.

A diagram like this can show what else may change when you change one line. To try it, ask your chat to list which lines need which, one per line, like "Line 3 needs line 2". Check each answer yourself. Keep the sentences as well, since each check belongs to a sentence.

This is an option, not a step. I found no test of how well AI reads such diagrams for specs. In a 2025 study of flowcharts, the two best models tested did better once the chart was turned into text, such as Mermaid. The authors also say their method struggles with more complex diagrams, such as dependency graphs. So keep yours small.

Go further

Skills

A skill is a ready-made set of instructions for an AI tool, so you don't have to paste the words yourself. Claude, ChatGPT and Gemini each have skills. Turn one on, then ask for the job in plain words.

Where to find skills in Claude, ChatGPT and Gemini
AppWhere to find skills
Claude AnthropicOpen Customize, then Skills. Skills need code execution (a setting that lets Claude run code for you) switched on. You usually find it under Settings, then Capabilities.
ChatGPT OpenAIIn the sidebar, choose Plugins, then the Skills tab.
Gemini GoogleOn gemini.google.com, choose Customize in the sidebar, then Skills.

If you can't find skills in ChatGPT, a Project can hold your spec, instructions and chats in one place. See OpenAI's help page on Projects in ChatGPT.

Skills that do a job for you
  • doc-coauthoring Anthropic · for the Claude app

    Write and test your spec. It guides you through gathering what you know, shaping the document and testing it in a new chat. If you can't use it, ask any AI chat to interview you instead, as in step 1.

  • Security-audit skill Cloudflare · needs a coding tool, an AI tool for programmers

    Check the safety. It turns a coding tool into a security checker for a folder of code. Use the four questions from step 4 first.

  • Agent Skills Addy Osmani · made for coding tools

    Write the spec first. Its /spec command is for defining what to build before any code. Its spec skill asks you questions until the requirements are concrete.

  • Superpowers Jesse Vincent · made for coding tools

    Turn your idea into a spec and a plan. It asks you questions to find out what you want, shows you the spec in short pieces, then breaks the work into small tasks.

  • code-review Matt Pocock · made for coding tools

    Review the finished work against your spec. It runs two reviews side by side: one against the project's coding standards, one against your spec. If it can't find a spec, it asks you where the spec is. If you say there is none, it skips that review and says so.

Only install skills from sources you trust, and read a skill from a less-trusted source before you switch it on. That is Anthropic's advice, because a malicious skill can make Claude do things you didn't intend, or leak your data. In February 2026 the security company Snyk found 76 confirmed malicious payloads among nearly 4,000 skills on two marketplaces. A payload here is harmful code that steals logins or data, or lets attackers back in.

When you're ready for coding tools, Anthropic's best-practices guide for Claude Code is a good next read.
