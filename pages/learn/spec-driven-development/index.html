A 10-minute scroll about spec-driven development

Write it down
before you build it

"Spec-driven development" is a long name for a simple habit. Before an AI builds anything, you write down what you want, in plain sentences. This page follows one small example: a shopping-list app.

Try it right away in step 7. If you're not sure a written spec suits your job, read Ask, Write or Draw? first.

Step 1 · The spec

Write down what the app should do

It is tempting to start by chatting: "Build me an app for my shopping list". The AI then decides small things itself, such as what ticking does. Spec-driven development changes the order. First you write down what the app must do, one plain rule per line: the spec. The AI can help you draft it, then builds from it.

Shopping-list app · what it must do · a made-up example

One of these lines would make the AI guess. Tap it.

Keep this one. You could check it by trying the finished app. Try another line.

Rewritten. "Easy" hides the choices: how big, where the Add button sits, what happens with an empty name. Say what you would see or do.

A real spec would be longer. What matters is the style: plain words, one rule per line.

Takeaway

Keep a line if you could check it by trying the app. Rewrite it if two people could read it differently.

Step 2 · Stages

Build it in four stages, one at a time

Don't ask the AI for the whole app at once. Ask for one stage at a time, and read what you get before you say "next". When something is wrong, go back to the stage where it started. Changing a sentence is quick. Finding out later that the whole app rests on a wrong guess is slow.

Try it · press the four stages · a made-up shopping-list run

Who does itYou tell the AI the idea. It writes the spec and asks what's unclear.

What you get

A spec, a page of plain sentences, like "I type an item and how many I need, and press Add".

What you check

Is this what I meant? Is anything missing?

Who does itThe AI proposes how to build it. You read the plan.

What you get

A short plan of the pieces: a box for the item, a box for the number, an Add button, and the list.

What you check

Does it cover every line? Try "Milk 2", then "Milk 1". As planned, you would get two Milk lines, and the spec says nothing about it. Add that rule as line 4, then ask for a new plan.

Who does itThe AI splits the plan into small tasks. You check the order.

What you get

1. Add an item and show the list. 2. Tick an item and move it to the bottom. 3. Remember the list. 4. Add to the number of an item that is already there.

What you check

Is the order sensible? Is any task too big to check on its own?

Who does itThe AI does one task at a time. You try each result.

What you get

A working piece, one task at a time. After task 1, you can type Milk and 2, press Add, and see "Milk 2".

What you check

Does it do what its line of the spec says? If not, say so before the next task.

Takeaway

A gap in the spec goes back to the spec. A fault in the app is fixed in the build.

Step 3 · Checks

Turn each line into a check

A check (engineers say "test") looks at one line of the spec and ends in pass or fail. Ask for the checks first, save them with your spec, and run them yourself. Anthropic's report says Claude 3.7 Sonnet occasionally took shortcuts to pass tests in coding tools like Claude Code. One form was changing the tests to match its code.

Takeaway

A good check has an answer you can work out yourself. Keep your own saved copy, and ask why whenever a check changes.

Step 4 · Safety

Write down the safety rules too

If a spec says nothing about what the app saves, or who may see it, the AI picks something. A real case: Moltbook, a social website whose founder said he built it with AI. In February 2026 the security company Wiz reported that anyone could read and change what it stored. I'm not saying a spec would have prevented that.

Four safety questions to ask your AI about any spec
  1. Who is allowed to see or change what? Being signed in doesn't mean being allowed to see everything.
  2. Where are passwords and other secret codes kept? Not written into the app itself.
  3. Is any shortcut you used while building, such as a login that lets anyone in, still open once people use the app?
  4. When something goes wrong, does the app show technical details that could help someone break in?
One more line for the spec, my ownWho is told when the app stops working. That can be you.

The four questions are in my words, from Cloudflare's free security-audit skill (June 2026). Paste them into your chat with your spec, and read the answers yourself. For the shopping list, one line covers it: "The list stays on my device. Nobody else can open it".

Takeaway

A spec gives you somewhere to write the safety rules down, so there's something to check.

Step 5 · When something breaks

The spec rebuilds the app, not its data

Apps do break: a change goes wrong, or someone deletes the wrong file. So save your spec, your plan and your checks as files you can find again. A new chat starts from nothing. Give it the files, and it carries on. Anthropic gives similar advice: once the spec is complete, start a new chat to build from it.

What you could lose
  • The chat you built it inIt does not come back, but a spec saved as a file lets you carry on where you were.
  • The app itselfThe spec, plan and checks may bring it back, by rebuilding. The new copy may differ, so run the same checks on it.
  • The data it keeps, such as your shopping listThe spec does not help. It comes back only from a saved copy. Ask the AI for an "Export my list" button.

Don't expect a perfect copy. Birgitta Böckeler, an engineer at Thoughtworks, had an AI write the code several times from the same spec, and the results varied.

Takeaway

The spec brings back the app, not what people typed into it. Keep a copy of the data somewhere else.

Step 6 · The good and the bad

What's good about it, and what isn't

Here is what people have reported, for and against. Use it to decide how much spec your own project needs. Step 8 helps you choose.

What people have reported · for and against

+For

  • Missing requirements are a common problem. A 2014–15 survey of 228 companies: 48% ranked incomplete or hidden requirements among their five most critical problems.About software projects in general, not specs.
  • A spec gives reviewers something to point to. A small 2026 trial (InfoQ, five reviewers): with the spec, 81% of findings could be tied to a named requirement; without it, none. Reviewers found about the same share of known problems either way.

−Against

  • It can be too much for a small job. Böckeler asked Kiro, an AI coding tool, to fix a small bug. The result was four "user stories" and sixteen acceptance criteria: "a sledgehammer to crack a nut". Kiro has since added a spec type for bug fixes.
  • It costs time, and it can drift. In the trial above, reviews took about 22 minutes longer with the spec. A Thoughtworks writer who supports the approach says "spec drift" and hallucination are "inherently difficult to avoid".
Takeaway

A spec gives you something to point to. It costs reading time, can go out of date, and the AI may not follow it.

Step 7 · Try it

The same idea, asked two ways

Press a message to send it, and try both ways. Then try it on your own idea. Tell an AI chat what you want and ask it to interview you. Then ask it to write the spec as short numbered sentences. A normal AI chat and a file of your own (Word, Google Docs or Notepad) are enough.

Takeaway

With "Just ask", the AI made choices you never made. With "Spec first", it asked before building, and you had checks to run.

Step 8 · How much spec

Match the spec to the risk

Not every job needs all of this. The four settings below are my own suggestion, each with an example job. Press a setting to see what it means, then pick the one that fits your idea. The last two are for bigger jobs.

How much spec · press a setting

Setting 1. Tell the AI what you want in one sentence, such as "Make the title blue", and check the result. Skip the spec. You see the result at once, and a wrong guess costs a few seconds.

Setting 2. Plain sentences for the main rules, and a check for each. If the app keeps data for you alone, one line says where it stays. A shopping list or a packing checklist is about this size.

Setting 3. Add rules for who may see what, where passwords and other secret codes are kept, and what happens when saving fails. Give each rule a check. Ask the four questions from step 4, then ask them again in a new chat, because one chat can miss things. Back up what the app saves, as step 5 explains. Other people's details raise the setting, even for a small tool.

Setting 4. Do everything in the full spec, then keep checking now and then that it still works once people use it. If many people will rely on it, a ready-made service, such as an online form or booking tool, may be the safer choice.

Takeaway

A small change needs one sentence. Other people's details need safety rules. A tool many people rely on needs all of it, and someone watching.

Before you go

That's the whole habit

Write it down, build in stages, check each line, write the safety rules, save the files, and match the spec to the risk.

My own try

I took the spec-first way for my own "about me" page. For me, it was the fastest page I have built in my career, and the one that fitted my needs best.

A skill is a ready-made set of instructions for an AI tool, so you don't have to paste the words yourself. Claude, ChatGPT and Gemini each have skills. Turn one on, then ask for the job in plain words.

Where to find skills in Claude, ChatGPT and Gemini
AppWhere to find skills

ChatGPT OpenAIIn the sidebar, choose Plugins, then the Skills tab.
Gemini GoogleOn gemini.google.com, choose Customize in the sidebar, then Skills.

If you can't find skills in ChatGPT, a Project can hold your spec, instructions and chats in one place. See OpenAI's help page on Projects in ChatGPT.

Skills that do a job for you
  • doc-coauthoring Anthropic · for the Claude app

    Write and test your spec. It guides you through gathering what you know, shaping the document and testing it in a new chat. If you can't use it, ask any AI chat to interview you instead, as in step 7.

  • Security-audit skill Cloudflare · needs a coding tool, an AI tool for programmers

    Check the safety. It turns a coding tool into a security checker for a folder of code. Use the four questions from step 4 first.

  • Agent Skills Addy Osmani · made for coding tools

    Write the spec first. Its /spec command is for defining what to build before any code. Its spec skill asks you questions until the requirements are concrete.

  • Superpowers Jesse Vincent · made for coding tools

    Turn your idea into a spec and a plan. It asks you questions to find out what you want, shows you the spec in short pieces, then breaks the work into small tasks.

  • code-review Matt Pocock · made for coding tools

    Review the finished work against your spec. It runs two reviews side by side: one against the project's coding standards, one against your spec. If it can't find a spec, it asks you where the spec is. If you say there is none, it skips that review and says so.

Only install skills from sources you trust, and read a skill from a less-trusted source before you switch it on. That is Anthropic's advice, because a malicious skill can make Claude do things you didn't intend, or leak your data. In February 2026 the security company Snyk found 76 confirmed malicious payloads among nearly 4,000 skills on two marketplaces. A payload here is harmful code that steals logins or data, or lets attackers back in.

When you're ready for coding tools, Anthropic's best-practices guide for Claude Code is a good next read.
