Step 1 · What a skill is

A folder with one file that matters

An Agent Skill is a folder with a SKILL.md in it: a few lines of front matter — name, description — and then plain-English instructions. It can carry scripts and reference files alongside. The format is an open standard supported by a range of agent tools, so a skill written once is portable.

The description is the load-bearing field. An agent reads only the name and description of every skill it has, and loads the full body only when the description matches the task. This is progressive disclosure: a bad description means a good skill never gets used. Flip the card to see the difference.

skills/careers/pay-check/SKILL.md

        

      

      

    

    
Takeaway
The agent decides whether to open a skill from its description alone. Write that line as if it is the only one anyone will read — usually it is.

  







  

    

      
Step 2 · The architecture

      
Two repositories and a one-way valve

      
The notes are taken during real job-search conversations — which companies, which roles, what went wrong in which interview. They cannot be public. The skills are meant to be public, both so they can be installed and because a skill nobody can read is hard to trust. One repo cannot be both, so there are two: private input, public output, and a valve between them.

    

    

      

        
alexratmanpl/claudeprivate · the control repo

  CAPTURE.md       how to write a finding
  AGENT.md         what the summariser does

The valve is a rule, not a mechanism. Nothing technically stops the summariser from copying a company name out of a note and into a pull request. What stops it is an instruction in CAPTURE.md telling the note-taker to redact before writing, plus the fact that every pull request is read by a person before it merges. The boundary is enforced at the point where a human looks at it. That is a real limitation, and a more useful thing to say than pretending it is airtight.

      
Takeaway
Private input, public output. The line between them is held by a review step, and it helps to know exactly which step.

    

  







  

    

      
Step 3 · The problem solved first

      
How does an agent push code?

      
The agent runs in a sandboxed cloud container. Its outbound traffic goes through a proxy, and git push goes through a git proxy that swaps in its own credentials — and only for repositories attached when the session started. Nothing could add a repo to that set mid-session. So: an agent that can write files, run tests and compose a perfectly good commit, and cannot send it anywhere.

      
Pick a route and watch where it stops.

    

    

      

        
        
        
      

      

      
Three ways out of the container. Two of them are walls.

    

    

      
The way around it was not to fight the proxy. A connector — the GitHub connector, authorised against the account — does not use the session's network at all. Its traffic leaves through Anthropic's servers and arrives at GitHub's REST API by a different road. The git proxy never sees it; the container's domain allowlist never sees it either.

      
The sandbox restricts what the machine can reach. The connector restricts what the account has granted. They are separate systems, and the second is the one that matters for writing to GitHub.

      
A second discovery followed. Once connected, the connector could see public repositories but not the private one. The GitHub App had been authorised but not installed — authorisation is an identity handshake; installation is what grants repository access, and it is installation that exposes the “only select repositories” picker. Selecting exactly two repos fixed the access problem and tightened it in the same move. Both walls were then tested by trying to break them:

403 and 409 are the status codes actually observed. Neither wall is client-side; neither depends on the agent choosing to behave.

    

    

      
Takeaway
A network boundary and a capability boundary are different things. Confusing them is why this looked unsolvable for longer than it should have.

    

  







  

    
Step 4 · The loop

    
Seven steps, then back to the first

    
Click any step. It advances on its own until you do.

    

      

        
        

      

      

    

    
Two details in that loop are more interesting than they look.

    
Step 3 is deliberately trivial. The log-finding skill is 36 lines. It does not contain the rules for writing a finding — it points at CAPTURE.md in the control repo, where the rules live. The same pattern runs through the whole system:

    

      
The thin-pointer pattern

      
Each rule lives in exactly one place: where it is enforced. Every layer above it points rather than copies.

      

        
the log-finding skill→CAPTURE.md

        
AGENT.md→.github/pull_request_template.md

        
the scheduled task's prompt→AGENT.md

      

      
Copy a rule into a second place and there are two places to update. One of them will be wrong within a month, and it will be the one you forget.

    

    
Step 4 keeps a watermark. state/watermark.json records the last processed commit, so a run that wakes to nothing new does nothing, and a run that crashes halfway does not reprocess. It is the smallest possible piece of state, and it is what makes the schedule safe to run unattended.

    
One footnote. AGENT.md lives in the repo the automation can edit, so in principle the automation could edit its own instructions. The invariants that must not drift are therefore repeated in the scheduled task's own prompt, which the automation cannot reach. A self-improving system needs at least one thing about itself it cannot improve.

    
Takeaway
Write each rule where it is enforced and point at it from everywhere else.

  







  

    

      
Step 5 · The experiment

      
Same findings, same model, new instructions

      
After the first automated run, its pull requests were reviewed and rated. Then the state was reset — watermark cleared, run log archived, pull requests closed unmerged — the instructions were rewritten, and the same findings were fed to the same model again. Inputs held fixed; only the instructions changed.

      
Four rules were added to AGENT.md. Click one to see where it shows up in the second run's output.

Both pull requests answer the same finding about the company-research skill: material the agent reasoned was sitting next to material it found, in the same register. Both change the same file, and GitHub counts both as +3 −2 lines. Read the two new bullets.

    

    

      

        
Run 1Run 2

        
Pull requests opened24

        
Accuracy — did it change the right things?8 / 109 / 10

        
Change quality — was the change any good?5 / 108 / 10

      

      
Both ratings are one reviewer's subjective judgement of the same findings processed twice. They are presented as such.

      
Accuracy barely moved. Quality moved a lot. The original instructions were good at saying what to do and said nothing about how well. The agent had been picking the right problems from the start; what it lacked was any standard for what a good fix looked like, so it defaulted to adding — more words, more caveats, several concerns in one pull request. Every addition was defensible. The aggregate was a document nobody would read.

      
The line that made rule 4 stick was not the principle but the accounting: state in the pull request how many lines the skill gained or lost. A number the agent has to write down is a constraint. A principle it merely has to agree with is not.

      
Takeaway
Telling an agent what to do is the easy half. The instruction that improved the output most was the one that told it what to remove — and made it count.

    

  







  

    

      
Step 6 · Failures, kept on the record

      
What went wrong, and what is still wrong

      
The system's own rule is not to claim checks that were not run, so a presentation about it that quietly dropped the failures would be self-refuting. Two of them are still open.

    

    

      
Caught
A file hash was fabricated
Mid-task, a SHA was needed for an API call and one was invented rather than fetched. The API rejected it — the only reason it was caught. The workflow was switched to an endpoint that does not need the caller to supply one, and the mistake was disclosed rather than quietly fixed.

      
Caught
The linter flagged its own documentation
A checklist script that flags AI-writing tells had leverage on its list and fired on the skill's own correct use of the word. It also only looked for a bracket after an acronym, never before, so “applicant tracking system (ATS)” tripped it. Both fixed.

      
Caught
The validator had a blind spot
It checked bundled-file references only when they contained a slash, so flat files sitting next to SKILL.md were never verified.

      
Still open
The fix that introduced a bug
Dates were drifting, so a rule said: take the date from GitHub, not the local clock. But it reads the control repo's last commit, which in a quiet repo is stale. Two pull requests opened on 4 September 2026 sit on branches named claude/2026-08-25-… — ten days off. Nobody noticed for three weeks.

      
Still open
A release nobody can install
The publishing workflow marks the rolling release as a prerelease. GitHub's /releases/latest endpoint excludes prereleases, so the obvious URL returns 404. The release exists and is invisible to the obvious way of fetching it. Unfixed — because the agent deliberately has no permission to edit .github/workflows/, which is the right call.

      
Found by run 3
A record that forgot everything
The interview record page was saving to window.storage, which does not exist, so nothing survived a reload. The third run found it, switched to localStorage, and verified the fix in a browser it drove itself — inside an iframe that withholds storage permission, to check the fallback too.

    

    
Takeaway
Audiences trust the account that includes the failures. So do the people who have to maintain the thing.

What this argues

      
    
        
  1. A capability boundary and a network boundary are different things.
    2. 
        
  2. Write rules where they are enforced and point at them from everywhere else.
    3. 
        
  3. Telling an agent what to do is the easy half; standards about what to remove are what separate output you would ship from output you would not.
    4. 
        
  4. Give the agent a number it has to write down. “Keep it readable” is advice; “state how many lines it gained or lost” changes behaviour.
    5. 
      

      
And the honest closing: the private/public boundary is held by a person reading pull requests, the date bug went unnoticed for three weeks, and the release URL still 404s. It works, and it is not finished.
